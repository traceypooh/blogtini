# blogtini v2 — design notes

Status: draft, 2026-10-02.

## Why
Anyone who posts to socials (half the world?) should be able to keep the highlights of their life
as markdown, in a free git repo, that lives forever.

And it's good for everyone who reads the web:
- crawlers and the Wayback Machine fetch the markdown, plus **one** theme JS shared by every page
  (and every blogtini site using that theme). Minimal storage, rich display.
- no JS, no network, 1000 years from now? It's still a text file. Obvious what each post is:
  title, date, tags, words.

## Goals (unchanged from TODO.md)
- zero config, zero *required* build
- parents can do it
- pull in info from multiple blogs — see [Combo sites](#combo-sites-you--your-friends-one-page)
- new: get your posts *out* of socials — see [Import your socials](#import-your-socials)

## The promise, restated
**No build step is required. An optional build step makes it better.**

Today we already have an optional build (the GitHub Action, plus git hooks). v2 makes that official,
with just **two modes**:

| mode | you publish | you get |
|------|-------------|---------|
| **built** | markdown files + the build step | `index.xml` (feed + sitemap + search index, one file) and a one-line `<head>` prepended to each post/page (title, image, description) |
| **raw** | markdown files with the `<script>` line, nothing else | each page renders itself; no site-wide index, search, clouds, recent posts |

Either way, if the JS never loads, the page still shows its text (see [Fail open](#fail-open)).

The build step's audience is the open web, not Google (Google runs our JS).
Things that *don't* run JS: Mastodon/Signal/iMessage/Slack link previews, RSS readers,
most other crawlers, Wayback capture metadata, a person with a hard drive in 1000 years.


## `index.xml` becomes the content index
It's our RSS feed today: title, link, date, empty description. Enrich it so the client can use it as
**both** the list of urls (what the sitemap does now) **and** the lunr search corpus.

```xml
<rss version="2.0"
     xmlns:atom="http://www.w3.org/2005/Atom"
     xmlns:content="http://purl.org/rss/1.0/modules/content/"
     xmlns:media="http://search.yahoo.com/mrss/">
  <channel>
    <title>Blogtini</title>
    <link>https://blogtini.com/</link>
    <lastBuildDate>Fri, 14 Feb 2025 00:00:00 -0800</lastBuildDate> <!-- newest post, NOT now -->
    ...
    <item>
      <title>Blogtini SEO</title>
      <link>https://blogtini.com/2024-07-blogtini-seo/</link>
      <guid>https://blogtini.com/2024-07-blogtini-seo/</guid>
      <pubDate>Sat, 06 Jul 2024 00:00:00 -0700</pubDate>
      <category domain="category">website</category>
      <category domain="tag">metadata</category>
      <category domain="tag">search engines</category>
      <description>We're now working on improved Search Engine Optimization ...</description>
      <media:content url="https://blogtini.com/img/seo.jpg" medium="image"/>
      <content:encoded><![CDATA[ ...the markdown body... ]]></content:encoded>
    </item>
  </channel>
</rss>
```

| what the client needs | RSS element |
|---|---|
| url | `<link>` |
| title | `<title>` |
| date | `<pubDate>` |
| tags, categories | `<category domain="tag">`, `<category domain="category">` |
| one-liner summary | `<description>` |
| featured image | `<media:content>` |
| body (search, summaries) | `<content:encoded>` — markdown, in CDATA |

- Items sorted by date, newest first (today they're sorted by dir name).
- Pages (eg: `about/`) get excluded from the feed — or marked, so the client can still find them.
  - open question: front matter `type: page`?  or `<category domain="type">page</category>`?
- Size: ~112 posts ≈ 500 KB text, ≈ 60 KB gzipped. One request instead of 112.
- `content:encoded` is normally HTML. We put markdown there because that's what we have and parse.
  Feed readers will show it as plain-ish text. Open question: ship rendered HTML there instead
  (build runs showdown), and keep markdown only for the client?  Or cap it, eg: only first N posts.


## `sitemap.xml` goes away (mostly)
Google accepts RSS 2.0 and Atom 1.0 feeds as sitemaps, alongside XML and plain text.
So `index.xml` *is* our sitemap. Tell crawlers about it either way:
- `robots.txt`: `Sitemap: https://blogtini.com/index.xml` — the build writes this; covers Google, Bing, etc.
- Google Search Console → Sitemaps report → submit `index.xml`. Optional; shows when Googlebot last read it.
- There's no "ping" anymore (Google retired its sitemap ping endpoint in 2023). Googlebot re-reads
  the sitemap on its own schedule.
- Google's caveat: a feed "only provides information on recent URLs" — that's about typical feeds
  holding the last N items. Ours lists everything, so no gap.


## Client loading order (`find_posts()` in index.js)
1. `index.xml` → `DOMParser` → `STORAGE.docs`. Done: no per-post fetches.  (**built**)
2. else `sitemap.xml` → fetch every post. Today's behavior, kept quietly for existing sites
   and hand-made sitemaps — not a documented mode.
3. else the current page alone.  (**raw**)

Raw ("current page alone") means:
- render this page's markdown, title, date, featured image
- show *this* post's tags and categories (as text, or links to `../index.html?tags/x`)
- link back to the top `index.html`
- hide: search, tag/category clouds, recent posts, previous/next

Bonus: the same feed parser reads *other* blogs' RSS/Atom — the TODO.md "followers' websites" idea.


## Fail open
Today, if the JS doesn't load, **the page is blank**:
- homepage: `<body class="homepage" style="display:none">`
- built posts: `HTML_TOP_LINE` starts with `<style>body{display:none}</style>`

JS shows the body only after it renders. If esm.ext.archive.org, blogtini.com, or JS itself is gone,
nobody sees anything — the markdown is right there in the file, hidden.

Fix, CSS only, no JS needed: hide briefly, then show regardless.
```html
<style>
  body { visibility: hidden; white-space: pre-wrap; animation: bt-show 0s 3s forwards }
  @keyframes bt-show { to { visibility: visible } }
</style>
```
JS sets `visibility: visible` (and drops `pre-wrap`) as soon as it renders, so normal visitors never wait.
If JS never arrives, after 3s you see the raw markdown — and `pre-wrap` keeps its line breaks,
so it reads like the text file it is.

Raw posts already fail open — they have no `display:none` in them. Only the homepage and **built**
posts need this fix.

Homepage: the build step can bake a plain markdown list of every post into the homepage body,
between markers, so a no-JS reader can still navigate:
```markdown
<!-- bt:index -->
- [Blogtini Turns One!](2025-02-blogtini-turns-one/index.html) 2025-02-14
- [Blogtini SEO](2024-07-blogtini-seo/index.html) 2024-07-06
<!-- /bt:index -->
```
(the client hides or skips that section when it renders the real post list)

### Self-host the JS deps
Libraries now come from esm.ext.archive.org: js-yaml, showdown, dayjs, lunr, lit,
redefine-custom-elements, and `krsort` from av.archive.org.
Vendor them into the repo (eg: `js/vendor/`) so a copy of the site dir is complete and works offline.
Sites that import `https://blogtini.com/index.js` still depend on blogtini.com — document
"copy `index.js` + `js/` + `theme/` into your repo" as the durable option.

### Versioned blogtini urls: GitHub tags via esm.ext.archive.org
deno.land/x is read-only now — "new modules and versions can no longer be published here".
`blogtini@1.0.4` is the last version there; it still loads.

Replacement: IA's esm.sh mirror serves any GitHub tag directly — no registry, no publish step,
just `git tag 1.0.5 && git push --tags`:
```
https://esm.ext.archive.org/gh/traceypooh/blogtini@1.0.5/index.js
https://esm.ext.archive.org/gh/traceypooh/blogtini@1.0.5/theme/future-imperfect/index.js
```
Tested with `internetarchive/httpd@v1.1.1` — imports fine in Deno, both forms:

| url | serves |
|---|---|
| `…/gh/OWNER/REPO@TAG/file.js` | a stub re-exporting an esbuild-**rebuilt** copy (`es2022/*.mjs`, minified) |
| `…/gh/OWNER/REPO@TAG/file.js?raw` | the file byte-for-byte (same as jsdelivr's `/gh/`, minus the third-party CDN) |

For blogtini, use the plain (rebuilt) form, everywhere, consistently:
- Mixing is risky: a `?raw` `index.js` imports its relative modules (`./js/…`, themes that import
  `index.js` back) as *rebuilt* copies → possibly two `cfg`/`state` instances.
- Blocker today: the plain form 500s — esbuild can't resolve index.js's theme-switcher
  ``import(`../theme/${theme}/index.js?...`)``. Make it non-analyzable (build the url in a
  variable first).
- CSS works already (200, `text/css`, CORS open) → drop the deno.land CSS special case
  in `path_to_theme_url()`.


## The build step: one Deno script
Replace `bin/sitemap`, `bin/rss`, `bin/seo` (zsh + yq + jq + GNU/BSD `date`) with one `bin/build.js` that
imports the **same** `markdown_parse()` the browser uses, so build and client always agree.

It writes:
- `index.xml` — as above
- `robots.txt` with `Sitemap: …/index.xml` (if there isn't one already)
- each post's head line (`HTML_TOP_LINE`): title, `og:image`, plus new
  `<meta name="description">` and `og:description` from the one-liner
- homepage `bt:index` link list
- `comments/*/index.json` (today's `bin/comments`, ported off jq)

Rules:
- idempotent and deterministic — running twice changes nothing (eg: `lastBuildDate` = newest post date)
- runs in the GitHub Action; git hooks stay optional (parents won't set up `core.hooksPath`)
- decide: is `index.xml` committed, or Action-only?  (it's untracked now)


## One-liners
Optional `description:` in front matter. If missing, the build uses `summarize_markdown()`.
The same string feeds: `<meta name="description">`, `og:description`, RSS `<description>`,
and search result snippets.


## Import your socials
The path for "half the world": fork the repo, upload your export, and your highlights are a site.

Socials offer data exports (largely thanks to GDPR). A converter turns one into blogtini posts:
`YYYY-MM-DD-slug/index.html` (front matter + markdown) and images into `img/`.

Exports to look at first:
- Mastodon: archive download — `outbox.json` (ActivityPub) + media
- Bluesky: repo export — a `.car` file (AT Protocol records) + blobs
- Instagram, Facebook: "Download your information" — pick JSON, not HTML
- X/Twitter: archive — `tweets.js` + media

Open questions:
- where does the converter run, for a parent?  A page on blogtini.com (in-browser, the export never
  leaves your computer) that hands back a zip — or a GitHub Action that reads an uploaded export.
- titles: social posts don't have them. First line, or date only?
- one post per social post, or one per day/week?
- repo size: photos and video add up. Git LFS (the Action already checks out with `lfs: true`)?


## Combo sites: you + your friends, one page
A site that interleaves 10 or 20 people's posts, newest first, with one shared tag cloud and search.
(Old-school "Planet" sites did this, eg: Planet Debian.)

Sitemaps can't do it for crawlers: the sitemaps.org protocol only allows urls on the sitemap's own host
(cross-host needs proof via each site's `robots.txt`). But blogtini's client doesn't care — it already
fetches absolute `https://` urls from a sitemap. With feeds it's simpler still: a combo site is a
list of feed urls.

**Main case: other blogtini sites.** Every blogtini `index.xml` has the same rich items (tags,
categories, summary, image, body), and GitHub Pages serves it CORS-open — so this works live,
no build. ~60 KB gzipped per feed → 20 friends ≈ 1.2 MB on first visit, then cached for the day.
```yaml
# config.yml
combo:
  - https://blogtini.com/index.xml
  - https://friend1.github.io/blog/index.xml
  - https://friend2.com/index.xml
  # bonus: same parser, thinner data
  - https://mastodon.social/@friend3.rss
```
The client fetches each, merges the items (keeps who wrote each one: the feed's `<title>`/`<link>`),
sorts by date, and builds the clouds and search over all of them. Post links go to the original sites —
nothing is copied, so no duplicate content.

**Bonus: any other RSS/Atom feed**, eg: friends still on socials. Thinner data, and some can't be
fetched from a browser (below).

CORS — can a browser on one site read another site's feed? Checked 2026-10-02:

| feed | `access-control-allow-origin` |
|---|---|
| GitHub Pages (`blogtini.com/index.xml`) | `*` — yes |
| Mastodon (`mastodon.social/@user.rss`) | `*` — yes |
| Bluesky (`bsky.app/profile/…/rss`) | none — **no** |

So blogtini and Mastodon friends work live, from the browser, no build. Feeds without CORS (Bluesky, many
WordPress sites) need the **built** mode: the Action fetches them and merges them into the combo
site's own `index.xml`.

Feed formats differ: Mastodon items have no `<title>`; Bluesky's are short; neither has our
`<category domain=…>` tags. The parser needs sensible defaults (eg: title = first line, tags from `#hashtags`).


## Wishlist: browsers and crawlers that understand this natively
If a `text/html` response starts with `---\n`, treat it as YAML front matter + markdown,
and honor one special front matter key:
```yaml
theme: ../theme.js    # relative or full url: one ES module import that "paints" the page
```
No theme? Render the markdown plainly. That's the whole blogtini idea as a web standard.

We already get this today with no browser help: the HTML parser sees the `<script>` inside the
front matter value and runs it; YAML sees an ordinary string. The key name doesn't matter to either,
so posts could say `theme: <script src="../theme.js" type="module"></script>` instead of `comment:` —
it reads like the wishlist. (`markdown_to_post()` ignores unknown keys; `config.yml`'s `theme:`
is a separate file, so no clash.)
