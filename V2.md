# blogtini v2 — design notes

Status: draft, 2026-10-02.

## Why
Anyone who posts to socials (half the world?) should be able to keep the highlights of their life
as markdown, in a free git repo, that lives forever.

And it's good for everyone who reads the web:
- crawlers and the Wayback Machine fetch the markdown, plus **one** theme JS shared by every page
  (and every blogtini site using that theme). Minimal storage, rich display.
- no JS, no network, 1000 years from now? It's still a text file. Obvious what each post is:
  title, date, tags, words.

## Goals (unchanged from TODO.md)
- zero config, zero *required* build
- parents can do it
- pull in info from multiple blogs — see [Combo sites](#combo-sites-you--your-friends-one-page)
- new: get your posts *out* of socials — see [Import your socials](#import-your-socials)

## The promise, restated
**No build step is required. An optional build step makes it better.**

Today we already have an optional build (the GitHub Action, plus git hooks). v2 makes that official,
with just **two modes**:

| mode | you publish | you get |
|------|-------------|---------|
| **built** | markdown files + the build step | `index.xml` (feed + sitemap + search index, one file) and a one-line `<head>` prepended to each post/page (title, image, fail-open style) |
| **raw** | markdown files with the `<script>` line, nothing else | each page renders itself; site-wide lists, clouds, recent posts only as far as the client can find your other posts (see [Finding posts](#finding-posts-without-a-build)) |

Either way, if the JS never loads, the page still shows its text (see [Fail open](#fail-open)).

The build step's audience is the open web, not Google (Google runs our JS).
Things that *don't* run JS: Mastodon/Signal/iMessage/Slack link previews, RSS readers,
most other crawlers, Wayback capture metadata, a person with a hard drive in 1000 years.


## `index.xml` becomes the content index
It's our RSS feed today: title, link, date, empty description. Enrich it so the client can use it as
**both** the list of urls (what the sitemap does now) **and** the lunr search corpus.

```xml
<rss version="2.0"
     xmlns:atom="http://www.w3.org/2005/Atom"
     xmlns:content="http://purl.org/rss/1.0/modules/content/"
     xmlns:media="http://search.yahoo.com/mrss/">
  <channel>
    <title>Blogtini</title>
    <link>https://blogtini.com/</link>
    <lastBuildDate>Fri, 14 Feb 2025 00:00:00 -0800</lastBuildDate> <!-- newest post, NOT now -->
    ...
    <item>
      <title>Blogtini SEO</title>
      <link>https://blogtini.com/2024-07-blogtini-seo/</link>
      <guid>https://blogtini.com/2024-07-blogtini-seo/</guid>
      <pubDate>Sat, 06 Jul 2024 00:00:00 -0700</pubDate>
      <category domain="category">website</category>
      <category domain="tag">metadata</category>
      <category domain="tag">search engines</category>
      <description>We're now working on improved Search Engine Optimization ...</description>
      <media:content url="https://blogtini.com/img/seo.jpg" medium="image"/>
      <content:encoded><![CDATA[ ...the markdown body... ]]></content:encoded>
    </item>
    <item>
      <title>About the Pooh</title>
      <link>https://blogtini.com/about/</link>
      ...
      <category domain="type">page</category>
      ...
    </item>
  </channel>
</rss>
```

| what the client needs | RSS element |
|---|---|
| url | `<link>` |
| title | `<title>` |
| date | `<pubDate>` |
| tags, categories | `<category domain="tag">`, `<category domain="category">` |
| page, not post | `<category domain="type">page</category>` |
| one-liner summary | `<description>` |
| featured image | `<media:content>` |
| body (search, summaries) | `<content:encoded>` — markdown, in CDATA |

Decided 2026-10-03:
- **body = markdown in `<content:encoded>`**, CDATA. Not rendered HTML (HTML-in-XML is gross; feed readers are
  a rounding error these days). It's what the client already parses. Summaries: client runs `summarize_markdown()`.
  Build must split any literal `]]>` in a body (`]]]]><![CDATA[>`).
- **`<description>`** = the one-liner, plain text (see [One-liners](#one-liners)).
- **`pubDate` = front matter `date`**, never bumped on edits — readers re-sort a bumped item to the top, and the
  client sorts by it too (an edit would make a 2009 post "recent"). No last-modified at all: Google only trusts
  lastmod when consistently accurate, and small sites get re-crawled anyway. (If ever wanted: `git log -1 --format=%cI`.)
- **pages included, marked** `<category domain="type">page</category>` — crawlers and search still find them.
  - post vs page: a **post** is dated and in the timeline (homepage list, recent posts, prev/next);
    a **page** is about/contact/favorites — nav menu, date doesn't matter.
  - rule: front matter `type: page` → page; no `type` / `type: post` → post. (Hugo's convention; poohtini posts
    already carry it)
- Items sorted by date, newest first (today they're sorted by dir name).
- Size: ~112 posts ≈ 500 KB text, ≈ 60 KB gzipped. One request instead of 112.


## `sitemap.xml` goes away (mostly)
Google accepts RSS 2.0 and Atom 1.0 feeds as sitemaps, alongside XML and plain text.
So `index.xml` *is* our sitemap. Tell crawlers about it either way:
- `robots.txt`: `Sitemap: https://blogtini.com/index.xml` — the build writes this; covers Google, Bing, etc.
- Google Search Console → Sitemaps report → submit `index.xml`. Optional; shows when Googlebot last read it.
- There's no "ping" anymore (Google retired its sitemap ping endpoint in 2023). Googlebot re-reads
  the sitemap on its own schedule.
- Google's caveat: a feed "only provides information on recent URLs" — that's about typical feeds
  holding the last N items. Ours lists everything, so no gap.

The build stops *writing* `sitemap.xml`. The client still *reads* one if there's no `index.xml`
(step 2 below) — so older sites and hand-made sitemaps keep working.
When blogtini.com's `sitemap.xml` starts 404ing: Search Console → Sitemaps → remove it, submit `index.xml`.
(`robots.txt` is written by the build, so its `Sitemap:` line follows automatically.)


## Client loading order (`find_posts()` in index.js)
The hard part of raw mode is always the same: **where does the list of urls come from?**
A static host won't tell a browser what files it has (GitHub Pages has no directory listings;
`python3 -m http.server` does, but only on your laptop). Each step below needs less setup and knows less:

1. `index.xml` → `DOMParser` → `STORAGE.docs`. Done: no per-post fetches.  (**built**)
2. else `sitemap.xml` → a "crickets" feed (items with just `<link>`) → same pipeline, fetch each post.
   (older sites, hand-made sitemaps)
3. else the repo's file list from the GitHub (or GitLab) API → fetch each post.  (**raw**)
4. else crawl local links, starting from the homepage → fetch each post.  (**raw**)
5. else this page alone.  (**raw**)

Everything above step 5 produces the same thing — a list of feed items, rich or bare — so there's one pipeline:
bare items get fetched and parsed for their front matter, rich ones don't.

Steps 3 and 4 don't mix: if 3 finds posts, skip 4 (merging the two lists is where duplicates and
url normalizing get messy).

A popular site will want the build anyway (one request vs N), so 2–5 only need to be good enough.

### Finding posts without a build

**GitHub tree API.** One call lists the whole repo, CORS-open:
```
GET https://api.github.com/repos/OWNER/REPO/git/trees/main            # top level only
GET https://api.github.com/repos/OWNER/REPO/git/trees/main?recursive=1 # everything
```
- No server-side filters; `recursive` is the only option (any value turns it on). Filter in the client:
  `type: "blob"`, path matches `\.(html|md)$`. Response caps at 100,000 entries / 7 MB (`truncated: true`).
- Top level is usually enough — posts are `YYYY-MM-slug/index.html`, so the dir names *are* the post list.
  blogtini.com, checked 2026-10-02: top level 29 entries / 8 KB; recursive 110 entries / 32 KB.
- OWNER/REPO: from the url (`OWNER.github.io/REPO/`). Custom domains (`CNAME`) can't be derived —
  needs a `repo:` line in `config.yml`.
- Public repos only (private → 404 unauthenticated). Fine: that's what free GitHub Pages serves.

Rate limits (unauthenticated):
- 60 requests/hour **per client IP**, one `core` bucket for *all* unauthenticated REST calls from that IP —
  not per repo. Visiting 3 blogtini sites = 3 calls from the same 60.
- Hitting it only affects that IP: `403`/`429`, `x-ratelimit-remaining: 0` until `x-ratelimit-reset`.
  Everyone else is fine.
- Shared IPs are common: plane wifi, VPN exits, iCloud Private Relay, phone carriers' CGNAT
  (api.github.com is IPv4-only, afaik). Still takes ~60 people on one exit IP loading blogtini sites
  (or other unauthenticated GitHub API calls) in the same hour. Rare, and the failure just drops to step 4.

Client rules:
- cache the list in localStorage for 1 hour, **keyed by OWNER/REPO** — `alice.github.io/blog` and
  `alice.github.io/recipes` are the same origin and share localStorage
- read `x-ratelimit-remaining` (exposed to JS via CORS); on `403`/`429` don't retry before `x-ratelimit-reset`
- response has `etag` + `cache-control: max-age=60`; the browser revalidates on its own. GitHub says `304`s
  don't count against the limit — maybe only when authenticated; untested.

**GitLab**: same idea, `OWNER.gitlab.io/REPO`:
```
GET https://gitlab.com/api/v4/projects/OWNER%2FREPO/repository/tree?per_page=100
```
Paginated (100 max per page), but blogtini's top level almost always fits in one.
Unverified: gitlab.com's unauthenticated limit (believed much looser than GitHub's) and CORS.

**Crawl local links.** The "copy markdown files into a dir, serve it, it just works" case
(caddy, any host). A homepage that links to its posts already *is* a sitemap:
- fetch the homepage, collect local links in its markdown, fetch each for its front matter
- one level covers the normal case; going a level or two deeper is cheap
- the built homepage's `bt:index` list (see [Fail open](#fail-open)) is this same link list, written by the build
  instead of by hand
- so the docs say "list your posts on your homepage" instead of "write a `sitemap.xml`"

**This page alone** means:
- render this page's markdown, title, date, featured image
- tag/category cloud of just this page's tags — as text, not links (a `../index.html?tags/x` link
  would land on a homepage that can't list anything either)
- link back to the top `index.html`
- hide: search, recent posts, previous/next

**Ruled out:**
- GitHub Pages + Jekyll making the list: Jekyll treats any file starting with front matter as a template —
  strips the front matter from the output and runs Liquid over the body, so our posts break. `.nojekyll` avoids
  that but also turns off `jekyll-sitemap` (which isn't on by default anyway).
- A Netlify (or similar) push hook that returns the site's paths: that's the built mode with a second service.
  The GitHub Action already runs on every push; the real hurdle (a parent enabling Actions/Pages) is the same.

Bonus: the same feed parser reads *other* blogs' RSS/Atom — the TODO.md "followers' websites" idea.


## Fail open
Today, if the JS doesn't load, **the page is blank**:
- homepage: `<body class="homepage" style="display:none">`
- built posts: `HTML_TOP_LINE` starts with `<style>body{display:none}</style>`

JS shows the body only after it renders. If esm.ext.archive.org, blogtini.com, or JS itself is gone,
nobody sees anything — the markdown is right there in the file, hidden.

Fix, CSS only, no JS needed: hide briefly, then show regardless.
```html
<style>body{animation:h 3s}@keyframes h{0%,to{visibility:hidden}}</style>
```

**Decided head line** (2026-10-03), the whole thing, one line:
```html
<!DOCTYPE html><title>Blogtini SEO</title><meta property="og:image" content="https://blogtini.com/img/seo.jpg"><style>body{white-space:pre-wrap;animation:h 3s}@keyframes h{0%,to{visibility:hidden}}</style>
```
Considered, skipped (keep the line small): `<meta charset=utf-8>` (GitHub Pages sends utf-8 in the HTTP header;
a saved-to-disk copy or another host could garble emoji) and `<meta name=viewport content=width=device-width>`
(no-JS phones show the raw text tiny; the JS adds it). Also no `<meta name="description">` / `og:description`.
Smallest robo top line: +39 chars over today's `<style>body{display:none}</style>`.
- the animation *is* the hiding: hidden at both ends for 3s, no `forwards`, so when it ends `body` falls back
  to its normal `visible`. Both keyframes are needed — `visibility` only "steps" to hidden at an endpoint that says so.
- JS reveals early with `document.body.style.animation = 'none'`
- optional `white-space:pre-wrap` (+21 chars) keeps the raw markdown's line breaks for no-JS readers.
  `white-space` inherits *into* shadow DOM, so JS must reset it when it renders.
- more trimming: `<html>`, `<head>`, `</head>`, `<body>` are all optional tags — the parser infers them.
  `<!DOCTYPE html><title>…</title><meta …><style>…</style>` then the markdown saves ~25 chars, nearly paying
  for the reveal. Keep `<!DOCTYPE html>` (standards mode). The homepage keeps its `<body class="homepage">`.
  Not yet tried with the real `main()`/`markdown_parse()` (should be fine: the head line is still one line
  starting with `<`). The Deno branch writes `</head><body>` explicitly — drop that.

**Tested 2026-10-03, Chrome** — [test/fail-open/](test/fail-open/) (serve the repo, open `test/fail-open/`).
All worked as expected, including with JS disabled in DevTools:
- no tags but `<!DOCTYPE html>`: still standards mode (`CSS1Compat`); `title, meta, style` land in `<head>`
- no JS: blank ~3s, then raw markdown (`nojs-prewrap/` keeps line breaks)
- JS at 1s: blank, then rendered; markdown never seen
- JS at 5s: raw markdown at 3s, swapped at 5s

CLS, measured by [test/fail-open/cls.js](test/fail-open/cls.js) (headless Chromium, 1280×800, Chrome's own
layout-shift events, so it works with JS off too):

| page | JS on | JS off |
|---|---|---|
| `shift-control/` (JS pushes visible text down 300px — proves the measuring works) | 0.1222 | 0 |
| `nojs/`, `nojs-prewrap/` | 0 | 0 |
| `js-fast/` (render at 1s, while hidden) | 0.0006 * | 0 |
| `js-slow/` (raw markdown visible at 3s, whole body replaced at 5s) | 0.0006 * | 0 |

\* the test's own `reveal.js` updating its "CLS: …" text at +1s, identical for both — not the hiding.

So **the slow-JS swap scores 0**: replacing all of `body.innerHTML` creates new elements, and a shift only counts
for an element that exists before *and* after. Real themes still get CLS from fonts, images, web component layout.
TODO: Firefox + Safari (visual check only — CLS is a Chrome metric).

Still hidden at first, on purpose: no flash of raw markdown (FOUC) and no layout shift (Google's CLS)
before the theme renders. CLS only counts shifts of *visible* content, so `visibility: hidden` is as good
as `display: none` there.

JS stops the animation as soon as it renders, so normal visitors never wait.
If JS never arrives, after 3s you see the raw markdown (with `pre-wrap`, line breaks and all — it reads like the
text file it is).

Who the 3s reveal is for: browsers that apply CSS but never run our JS — JS off, NoScript, a blocking proxy,
esm.ext.archive.org / blogtini.com down, a browser too old for ES modules. Not screen readers (they ride along
in normal JS browsers, and correctly skip the body until it's revealed) and not crawlers / text browsers
(they don't apply CSS, so they see the text regardless).

CLS: zero from the hiding, as long as the JS renders inside 3s. Slower than that (counted — Google's numbers come
from real Chrome visits), the raw markdown shows and then gets replaced. Possibly scores less than feared:
a shift only counts for an element present before *and* after, and `bt_body()` replaces all of `body.innerHTML`.
Unmeasured. Fonts, images without width/height, and web component layout after render are likely bigger CLS factors.
The 3s clock starts at first style/render, not at the request.

### Options: hiding the body until the theme renders

| option | no flash / CLS | crawlers w/o JS | people w/o JS | notes |
|---|---|---|---|---|
| nothing hidden (raw posts today) | ✗ raw markdown flashes, then swaps | ✓ | ✓ raw text | simplest; FOUC on every visit |
| `<style>body{display:none}</style>` (built posts + homepage today) | ✓ | ✓ CSS ignored | ✗ blank forever | |
| **`visibility: hidden` + 3s CSS reveal** (above) | ✓ if JS < 3s | ✓ | ✓ after 3s | **chosen.** screen readers skip it until revealed |
| `opacity: 0` + 3s CSS reveal | ✓ if JS < 3s | ✓ | ✓ after 3s | invisible text stays in the a11y tree: screen readers read it, Tab/click hit links in it. CLS for opacity-0: unsure |
| `<body hidden>` | ✓ | mostly ✓; reader-mode (Readability) skips `hidden` | ✗ blank | only the UA rule `[hidden]{display:none}`. CSS *can't* remove the attribute, but an author rule beats the UA one: `body[hidden]{display:block; visibility:hidden; animation…}` — at which point it's the chosen row plus an attribute that only makes reader-mode skip it |
| `<template>` wrapper, JS clones it out | ✓ | ✗ spec parsers (browsers, parse5, html5lib) put it in a separate fragment; crude tag-strippers may still keep the text | ✗ never shown, no CSS can reveal it | inert (no image loads / scripts) — not needed here. Raw posts would need a closing `</template>` |
| `<template shadowrootmode>` (declarative shadow DOM) | — | varies | ✓ renders with no JS | not a hiding tool — the opposite. Shows a *server-rendered* component before JS; would need a build that renders `bt-*` to HTML. Someday idea |
| `<body-blogtini>` wrapper + `:not(:defined){visibility:hidden}` | ✓ if JS < 3s | ✓ | ✓ only with the same 3s reveal | unknown element renders inline, hides nothing by itself. Only gain: auto-reveals when `customElements.define()` runs. Breaks `markdown_parse()` (`body.innerHTML` would start with `<body-blogtini>---`) |

Careful with `:not(:defined){visibility:hidden}` in general: an element with a declarative shadow root is still
`:not(:defined)` until its JS loads, so that rule hides exactly what SSR made visible.

Raw posts already fail open — they have no `display:none` in them. Only the homepage and **built**
posts need this fix.

Homepage: the build step can bake a plain markdown list of every post into the homepage body,
between markers, so a no-JS reader can still navigate:
```markdown
<!-- bt:index -->
- [Blogtini Turns One!](2025-02-blogtini-turns-one/index.html) 2025-02-14
- [Blogtini SEO](2024-07-blogtini-seo/index.html) 2024-07-06
<!-- /bt:index -->
```
(the client hides or skips that section when it renders the real post list — and in raw mode,
a hand-written list here is what the client crawls; see [Finding posts](#finding-posts-without-a-build))

### Self-host the JS deps
Libraries now come from esm.ext.archive.org: js-yaml, showdown, dayjs, lunr, lit,
redefine-custom-elements. (`krsort` etc. from av.archive.org: done, now in `js/text.js` — see Cleanups.)
Vendor them into the repo (eg: `js/vendor/`) so a copy of the site dir is complete and works offline.
Sites that import `https://blogtini.com/index.js` still depend on blogtini.com — document
"copy `index.js` + `js/` + `theme/` into your repo" as the durable option.

### Versioned blogtini urls: GitHub tags via esm.ext.archive.org
deno.land/x is read-only now — "new modules and versions can no longer be published here".
`blogtini@1.0.4` is the last version there; it still loads.

Replacement: IA's esm.sh mirror serves any GitHub tag directly — no registry, no publish step,
just `git tag 1.0.5 && git push --tags`:
```
https://esm.ext.archive.org/gh/traceypooh/blogtini@1.0.5/index.js
https://esm.ext.archive.org/gh/traceypooh/blogtini@1.0.5/theme/future-imperfect/index.js
```

**Blogtini JS imports** You can use the latest blogtini JS always, or a pegged versioned (longer url):
```
https://blogtini.com/index.js
https://esm.ext.archive.org/gh/traceypooh/blogtini@1.0.5/index.js

```


Tested with `internetarchive/httpd@v1.1.1` — imports fine in Deno, both forms:

| url | serves |
|---|---|
| `…/gh/OWNER/REPO@TAG/file.js` | a stub re-exporting an esbuild-**rebuilt** copy (`es2022/*.mjs`, minified) |
| `…/gh/OWNER/REPO@TAG/file.js?raw` | the file byte-for-byte (same as jsdelivr's `/gh/`, minus the third-party CDN) |

For blogtini, use the plain (rebuilt) form, everywhere, consistently:
- Mixing is risky: a `?raw` `index.js` imports its relative modules (`./js/…`, themes that import
  `index.js` back) as *rebuilt* copies → possibly two `cfg`/`state` instances.
- Blocker today: the plain form 500s — esbuild can't resolve index.js's theme-switcher
  ``import(`../theme/${theme}/index.js?...`)``. Make it non-analyzable (build the url in a
  variable first).
- CSS works already (200, `text/css`, CORS open) → drop the deno.land CSS special case
  in `path_to_theme_url()`.


## The build step: one Deno script
Replace `bin/sitemap`, `bin/rss`, `bin/seo` (zsh + yq + jq + GNU/BSD `date`) with one `bin/build.js` that
imports the **same** `markdown_parse()` the browser uses, so build and client always agree.

It writes:
- `index.xml` — as above
- `robots.txt` with `Sitemap: …/index.xml` (if there isn't one already)
- each post's head line — see [the decided head line](#fail-open)
- homepage `bt:index` link list
- `comments/*/index.json` (today's `bin/comments`, ported off jq)
- *not* `sitemap.xml` anymore

Keep `bin/build` as the entry point (other sites' workflows call `blogtini.yml@main`, which runs
`./_blogtini/bin/build`) — it just runs `bin/build.js`. Client side, swap `style.display = 'block'` reveals for
`style.animation = 'none'` (+ reset `white-space`).

Rules:
- idempotent and deterministic — running twice changes nothing (eg: `lastBuildDate` = newest post date)
- head line: committed posts never have one — only the CI checkout gets it, so the build always starts clean.
  Today's skip-if-`startsWith(HTML_TOP_LINE)` (`index.js` `main()`, `globalThis.Deno` branch) only matters for
  local test runs. Nicer for `bin/build.js`: match "first line starts with `<`" and *replace* it, so re-running
  locally is a no-op and a changed `HTML_TOP_LINE` can't stack a second line.
- runs in the GitHub Action; git hooks stay optional (parents won't set up `core.hooksPath`)
- decide: is `index.xml` committed, or Action-only?  (it's untracked now)


## One-liners
Optional `description:` in front matter. If missing, the build uses the start of the first paragraph that has
text, as plain text, up to 300 chars.
- **in the feed**: RSS `<description>` (feed readers show it as the preview).
- **not in the head line** (2026-10-03): no `<meta name="description">` / `og:description` for now, to keep
  the line small — an acceptable casualty.
- someday: search result snippets could use it too.


## Import your socials
The path for "half the world": fork the repo, upload your export, and your highlights are a site.

Socials offer data exports (largely thanks to GDPR). A converter turns one into blogtini posts:
`YYYY-MM-DD-slug/index.html` (front matter + markdown) and images into `img/`.

Exports to look at first:
- Mastodon: archive download — `outbox.json` (ActivityPub) + media
- Bluesky: repo export — a `.car` file (AT Protocol records) + blobs
- Instagram, Facebook: "Download your information" — pick JSON, not HTML
- X/Twitter: archive — `tweets.js` + media

Open questions:
- where does the converter run, for a parent?  A page on blogtini.com (in-browser, the export never
  leaves your computer) that hands back a zip — or a GitHub Action that reads an uploaded export.
- titles: social posts don't have them. First line, or date only?
- one post per social post, or one per day/week?
- repo size: photos and video add up. Git LFS (the Action already checks out with `lfs: true`)?


## Combo sites: you + your friends, one page
A site that interleaves 10 or 20 people's posts, newest first, with one shared tag cloud and search.
(Old-school "Planet" sites did this, eg: Planet Debian.)

Sitemaps can't do it for crawlers: the sitemaps.org protocol only allows urls on the sitemap's own host
(cross-host needs proof via each site's `robots.txt`). But blogtini's client doesn't care — it already
fetches absolute `https://` urls from a sitemap. With feeds it's simpler still: a combo site is a
list of feed urls.

**Main case: other blogtini sites.** Every blogtini `index.xml` has the same rich items (tags,
categories, summary, image, body), and GitHub Pages serves it CORS-open — so this works live,
no build. ~60 KB gzipped per feed → 20 friends ≈ 1.2 MB on first visit, then cached for the day.
```yaml
# config.yml
combo:
  - https://blogtini.com/index.xml
  - https://friend1.github.io/blog/index.xml
  - https://friend2.com/index.xml
  # bonus: same parser, thinner data
  - https://mastodon.social/@friend3.rss
```
The client fetches each, merges the items (keeps who wrote each one: the feed's `<title>`/`<link>`),
sorts by date, and builds the clouds and search over all of them. Post links go to the original sites —
nothing is copied, so no duplicate content.

**Bonus: any other RSS/Atom feed**, eg: friends still on socials. Thinner data, and some can't be
fetched from a browser (below).

CORS — can a browser on one site read another site's feed? Checked 2026-10-02:

| feed | `access-control-allow-origin` |
|---|---|
| GitHub Pages (`blogtini.com/index.xml`) | `*` — yes |
| Mastodon (`mastodon.social/@user.rss`) | `*` — yes |
| Bluesky (`bsky.app/profile/…/rss`) | none — **no** |

So blogtini and Mastodon friends work live, from the browser, no build. Feeds without CORS (Bluesky, many
WordPress sites) need the **built** mode: the Action fetches them and merges them into the combo
site's own `index.xml`.

Feed formats differ: Mastodon items have no `<title>`; Bluesky's are short; neither has our
`<category domain=…>` tags. The parser needs sensible defaults (eg: title = first line, tags from `#hashtags`).


## Wishlist: browsers and crawlers that understand this natively
If a `text/html` response starts with `---\n`, treat it as YAML front matter + markdown,
and honor one special front matter key:
```yaml
theme: ../theme.js    # relative or full url: one ES module import that "paints" the page
```
No theme? Render the markdown plainly. That's the whole blogtini idea as a web standard.

We already get this today with no browser help: the HTML parser sees the `<script>` inside the
front matter value and runs it; YAML sees an ordinary string. The key name doesn't matter to either,
so posts could say `theme: <script src="../theme.js" type="module"></script>` instead of `comment:` —
it reads like the wishlist. (`markdown_to_post()` ignores unknown keys; `config.yml`'s `theme:`
is a separate file, so no clash.)


## Cleanups found along the way
- [x] **Google indexing (2026-10-03):** `av.archive.org/robots.txt` became `Disallow: /` sometime between
      2025-03-25 (404, Wayback) and 2025-08-20. Googlebot honors robots.txt for page *resources* too, so it
      couldn't fetch `strings.js`; a failed static `import` kills the whole module graph, so `index.js` never ran and
      every post rendered as `body{display:none}` — blank. Likely why `site:blogtini.com` shows just the homepage.
      Fixed: copied `friendly_truncate`, `krsort`, `vsort`, `vrsort` verbatim into `js/text.js`.
      Still on the old import: any site pinned to `deno.land/x/blogtini@1.0.4` (option: allow `/js/` in av's robots.txt).
      Confirm in Search Console → URL Inspection → Test live URL → View tested page (screenshot, blocked resources).
      Lesson: every runtime import host must allow crawlers — another reason to vendor deps.
- [ ] port forward from `hugo-future-imperfect-slim` (the Hugo original of this theme, with years of fixes):
      image lazy loading and more. (Sidebar "See More" → `#postN` done 2026-10-03, + optional `view_more_posts_link`.)
      Lazy loading: add `loading="lazy"` to *every* `<img>` in the rendered HTML (eg: post-process
      `markdown_to_html()` output), so raw `<img>` tags people paste into markdown get it too — Hugo's image render
      hook only sees markdown `![]()` images, so raw tags miss out there (eg: some poohbot posts).
- [ ] build skips dirs named `test`, `theme`, `js`, `img`, `comments`, `node_modules`, `.*`, `_*` — a real post
      dir with one of those names would be skipped too. Maybe a front matter `draft: true` instead/as well.
      (Old `bin/sitemap` didn't skip `test/`, so live blogtini.com listed `test/fail-open/*` as its 4 newest posts.)
- [x] hand-made / other tools' `index.xml`: most feeds put the body as HTML in `<description>` and have no
      `<content:encoded>`, so `posts_from_feed()` loaded every post w/o a body — and the homepage crashed

      Fixed: a feed w/ no `<content:encoded>` at all is ignored (falls back to sitemap / crawl), and an empty
      body stays `''`. Someday maybe: use `<description>` HTML as the body instead (showdown passes HTML through).

      leaks viewer IPs + commenter email hashes. Use local initials/identicons.
